# 项目时间线与视频版本数据流排查

> 排查日期：2026-07-11  
> 范围：`frontend/src/components/projects/ProjectSheet.tsx`、项目事件、渲染任务、视频资产

## 结论与修复状态

截图中“视频待审核 v1”和“视频待审核 v2”点开后显示同一条视频，**已确认存在前端取数错误**：历史视频节点没有拿到自身的 `video_asset_id`，`ProjectSheet` 会回退为项目的 `currentVideoAsset.id`，也就是最新一次渲染的视频。因此，任意历史视频节点都可能播放最新视频。

另外，视频生成链路存在一个独立的版本冻结缺口：创建 `render_video` 任务时未保存 `code_version_id`，`RenderWorker` 执行任务时也忽略任务版本、改读 `project.current_code_version_id`。在当前工作流严格串行的正常路径中，通常仍会渲染刚审核通过的代码；但只要任务排队期间当前代码发生变化、旧任务被重置或发生并发操作，就可能渲染到与任务创建时不一致的代码版本。

因此，本次截图**不能据此断定 v1、v2 真的使用了同一份代码渲染**；但可以确定 UI 无法正确区分两份视频，且后端没有完整保留“时间线节点 → 视频资产 → 代码版本”的可审计关联。

本次已实施修复：新渲染任务会冻结 `code_version_id`；Worker 只使用该冻结版本；渲染完成信号会将视频资产与代码版本写入 `video_review`（并沿用到 `published`）状态事件；历史视频不再回退播放当前最新视频。旧事件缺少资产关联时，界面会明确提示无法安全播放。

## 当前数据模型与权威字段

| 实体 | 关键字段 | 当前语义 |
| --- | --- | --- |
| `video_projects` | `current_code_version_id` | 项目此刻生效的代码版本（指针，不是历史快照） |
| `video_projects` | `current_video_asset_id` | 项目此刻最新视频资产（指针，不是历史快照） |
| `worker_tasks` | `code_version_id` | 设计上应记录渲染任务绑定的代码版本；当前创建渲染任务时未写入 |
| `video_assets` | `code_version_id` | 实际渲染完成的视频与代码版本的关系；这是视频版本归属的核心证据 |
| `project_events` | `payload` | 时间线显示的数据来源；当前视频审核进入事件未写入视频资产 ID |

项目约束中不存在数据库外键，因此上述关系全由应用层写入和校验。

## 时间线与右侧详情当前如何组织

### 1. 时间线数据源

`ProjectSheet` 同时请求：

```text
GET /api/projects/{project_id}/events
GET /api/projects/{project_id}/narrative-versions
GET /api/projects/{project_id}/code-versions
GET /api/projects/{project_id}                 # 含 currentVideoAsset
```

时间线只渲染 `project_events` 中 `event_type = status_change` 的记录。`to_status` 决定内容类型：

```text
narrative_review -> narrative
code_review      -> code
video_review     -> video
published        -> video
```

叙事和代码节点优先使用事件 payload 的：

```json
{
  "content_type": "narrative | code",
  "content_version_id": "...",
  "content_version_number": 1
}
```

如果事件缺少这些字段，前端才会按事件时间从版本列表中猜测最近版本。审核结论（`review_verdict`）在两个同类状态节点之间查找，并显示“通过/驳回”和驳回意见。

### 2. 当前详情与历史详情

未点时间线时，右侧使用项目的**当前指针**：

```text
代码：GET /code -> current_code_version_id
叙事：GET /narrative -> current_narrative_version_id
视频：GET /project -> current_video_asset_id -> GET /video-url?asset_id=...
```

点叙事/代码历史节点时，右侧根据节点的 `content_version_id` 调用版本详情 API，因此可读取对应历史版本。

点视频历史节点时，前端希望从该状态事件的 `payload.video_asset_id` 读取资产 ID，再调用：

```text
GET /api/projects/{project_id}/video-url?asset_id={video_asset_id}
```

但现在这个字段未被写入，导致以下回退逻辑生效：

```ts
selectedNode.videoAssetId ?? projectDetail.currentVideoAsset.id
```

所以历史 v1、v2 均使用 `currentVideoAsset.id`，播放最新视频。截图中选择的是 v1，右侧显示的实际是项目当前视频（在 v2 渲染完成后即为 v2），不是 v1。

## 端到端证据链

### A. 为什么历史视频一定可能重复：事件未记录资产

1. `RenderWorker` 完成渲染后创建/更新 `VideoAsset`，并将 `video_projects.current_video_asset_id` 改为该资产。
2. `BaseWorker` 发给 Temporal 的完成信号含 `asset_id`：

   ```json
   { "task_id": "...", "success": true, "asset_id": "..." }
   ```

3. `VideoProductionWorkflow` 收到成功信号后只进入 `video_review` 状态：

   ```text
   _update_status(project_id, "video_review")
   ```

   没有把 `asset_id` 放进状态事件 payload。
4. `update_project_status()` 只会自动补充 narrative/code 的 `content_version_id`；它没有读取或写入视频资产信息。
5. `EventsSection` 因此得到 `videoAssetId = null`，再回退为 `currentVideoAsset.id`。

结论：这不是播放器缓存或 presigned URL 缓存导致，而是历史节点关联键缺失造成的确定性错误。

### B. 渲染任务是否也会“拿错代码”

当前实际链路：

```text
代码审核通过
  -> Temporal 调用 submit_video_generation_task(project_id)
  -> 新建 worker_tasks(render_video)，但 code_version_id = NULL
  -> RenderWorker 执行时读取 project.current_code_version_id
  -> 用该 CodeVersion.scenes 渲染
  -> VideoAsset.code_version_id = 执行时读到的版本
```

这与表设计和技术方案的预期不一致：`worker_tasks.code_version_id` 本应是渲染任务绑定的代码版本，`video_assets.code_version_id` 则记录最终产物实际使用的代码版本。

正常串行工作流下，审核通过后立即提交任务且没有其他代码变更，渲染版本大概率正确。风险出现在任务创建和 Worker 实际开始之间：

- 管理操作或重置重新排队；
- 旧任务尚未被取消即出现新的代码版本；
- 多 Worker/重复投递/异常恢复造成旧任务延后执行；
- 未来增加并行或人工操作入口。

此时 Worker 会渲染“执行当刻的当前代码”，而非“该任务被提交时审核通过的代码”。这属于后端版本绑定缺陷，但不能从截图单独证明已经发生。

## 对截图中项目的核验方式

以数据库结果为准，不要依据 UI。对该项目执行以下查询（将 `{project_id}` 替换为项目 UUID）：

```sql
-- 1. 所有视频资产及其实际关联代码版本：判断两次是否真的渲染了同一代码
SELECT
  va.id AS video_asset_id,
  va.status,
  va.code_version_id,
  cv.version_number AS code_version_number,
  va.video_file_key,
  va.created_at
FROM video_assets va
LEFT JOIN code_versions cv ON cv.id = va.code_version_id
WHERE va.project_id = '{project_id}'
ORDER BY va.created_at;

-- 2. 渲染任务是否冻结了代码版本：当前实现预计大多为 NULL
SELECT
  id AS task_id,
  status,
  code_version_id,
  output_payload,
  created_at,
  started_at,
  completed_at
FROM worker_tasks
WHERE project_id = '{project_id}'
  AND task_type = 'render_video'
ORDER BY created_at;

-- 3. 时间线视频审核节点是否具备资产关联：当前 video_review payload 通常没有 video_asset_id
SELECT id, from_status, to_status, payload, created_at
FROM project_events
WHERE project_id = '{project_id}'
  AND event_type = 'status_change'
  AND to_status IN ('video_review', 'published')
ORDER BY id;
```

判读：

- 两条 `video_assets` 的 `code_version_id` 不同：后端实际渲染了不同代码，截图重复纯属历史详情取错资产。
- 两条 `video_assets` 的 `code_version_id` 相同：两次确实渲染了同一代码；仍需通过任务时间、审核/重试事件进一步判断这是业务上的“重试同版”还是版本冻结缺失导致。
- `worker_tasks.code_version_id` 为 `NULL`：确认任务未冻结版本。
- `video_review` 事件没有 `video_asset_id`：确认该节点无法可靠定位历史视频。

## 建议的修复契约

### 必须修复：视频时间线可追溯性

渲染完成信号中的 `asset_id` 应在进入 `video_review` 时写入事件 payload，统一命名为 `video_asset_id`；同时写入 `code_version_id`（以及可选的 `code_version_number`）以便审计。

目标事件示例：

```json
{
  "video_asset_id": "asset-uuid",
  "code_version_id": "code-uuid",
  "code_version_number": 2
}
```

前端历史视频节点只应使用该 `video_asset_id`，**不能**在历史节点回退到 `currentVideoAsset.id`。对于历史旧数据，建议显示“该历史记录未保存视频资产关联，无法播放”，避免静默播放错误视频。

### 必须修复：渲染任务版本冻结

提交任务时读取 `project.current_code_version_id`，校验存在后写入：

```text
worker_tasks.code_version_id = project.current_code_version_id
```

`RenderWorker` 必须优先（建议仅）读取 `task.code_version_id`，而不是读取 `project.current_code_version_id`。创建 `VideoAsset` 时沿用同一个 ID。这样“任务、渲染输入、视频资产、时间线节点”形成一条不可变链路。

### 推荐补充：状态更新接口显式携带产物引用

`update_project_status()` 可以增加一个明确的 payload 契约；调用方传入来自 `render_completed` 的资产 ID。不要依赖该函数再查询 `current_video_asset_id`，因为这会在未来并发时重新引入“当前指针覆盖历史”的问题。

## 期望的最终关联图

```text
审核通过的 CodeVersion
        │（冻结 code_version_id）
        ▼
WorkerTask(render_video)
        │（使用 task.code_version_id 渲染）
        ▼
VideoAsset(code_version_id)
        │（render_completed.asset_id）
        ▼
ProjectEvent(to_status=video_review, payload.video_asset_id)
        │
        ▼
ProjectSheet 历史视频节点 -> /video-url?asset_id=该节点资产
```

`video_projects.current_*` 仍可保留给当前详情页快速读取，但不可作为历史节点的回退数据源。

## 回归验收场景

1. 完成代码 v1 渲染，记录视频资产 A，进入视频审核 v1。
2. 驳回至代码审核，生成/编辑为代码 v2，再渲染得到视频资产 B，进入视频审核 v2。
3. 点击时间线 v1：请求必须为 `video-url?asset_id=A`，播放 A；点击 v2：请求必须为 `video-url?asset_id=B`，播放 B。
4. 在 v1 任务入队、但尚未执行时将项目当前代码改为 v2；v1 Worker 仍必须加载 `task.code_version_id = v1` 并生成 `VideoAsset.code_version_id = v1`。
5. 为缺少 `video_asset_id` 的历史旧事件点击视频节点：显示不可用提示，不得播放项目最新视频。

## 涉及代码位置

- 前端历史视频回退：`frontend/src/components/projects/ProjectSheet.tsx` 的 `selectedVideoAssetId` 和 `EventsSection`。
- 视频状态事件写入：`backend/app/workflows/video_production.py` 的 `_generate_and_review_video()` 与 `backend/app/workflows/activities.py` 的 `update_project_status()`。
- 渲染任务创建：`backend/app/workflows/activities.py` 的 `submit_video_generation_task()`。

- 完成信号透传：`backend/app/workers/base.py` 的 `BaseWorker._process_task()`。
